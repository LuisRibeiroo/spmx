---
title: APFS clonefile
description: Why spmx clones with copy-on-write instead of copying or symlinking.
---

`clonefile()` is an APFS system call that creates a new file or directory whose contents share the same physical blocks as the source. Nothing is copied until one side is modified; then only the changed blocks are allocated.

## Why not symlinks

Xcode and Flutter tooling often fail on symlinks inside `SourcePackages/artifacts`: XCFramework signature validation, `xcodebuild` sandboxing and relative paths in `workspace-state.json` all assume real files. A clone looks like a normal directory tree, so none of that breaks.

## Why not plain copies

A plain copy duplicates every byte. With heavy binary SDKs, a handful of worktrees can cost gigabytes. A clone costs only metadata.

## Fallback

If `clonefile()` fails because the volume is not APFS (`ENOTSUP`) or the store and the worktree are on different volumes (`EXDEV`), spmx falls back to a regular recursive copy and mentions it with `--verbose`. Everything still works; you just lose the disk savings.

## Measuring the cost

Because `clonefile()` gives each clone its own inode while sharing the underlying physical blocks, `du` and Finder count every clone at its full logical size—making `DerivedData` and `~/.spmx/store` look larger than the actual disk space used. To see real physical usage, compare free space on the volume with `df -h /` (or `diskutil apfs list`), which is how the [benchmarks](/benchmarks) measure disk, or inspect estimated savings directly with `spmx`:

```bash
spmx store status   # includes an estimate of copy-on-write savings
df -h /             # real physical space available on your APFS volume
```
